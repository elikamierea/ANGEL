# Agent Console とツール呼び出し

Agent Console は、組み込みの agent と直接協働する場所です。

実用的な観点から言えば、使い始める前に agent システム内部のオーケストレーション全体を理解する必要はありません。より重要なのは：

- どう話しかけるか
- 何をしてもらうか
- いまその作業をこなせるかをどう判断するか
- その能力の限界をどう理解するか

## まず何として捉えるか

最も実用的なメンタルモデルは通常これです：

- 単なるチャットボックスではない
- 一言で常に作業全体を完璧に終える魔法のボタンでもない
- **プロジェクトの文脈を読み、現在の設計を理解し、ツールを使って作業を遂行しようとする協働アシスタント**として理解するのがよい

そのため最も向いているのは、漠然とした大きな願望ではなく、次のようなものです：

- 明確な目標
- 明確な範囲
- 優先してほしい明確な最初の一歩

## ユーザーは agent とどう対話すべきか

### 1. 作業をできるだけ具体的にする

次のように言うより：

- 「このプロジェクトを良くして」

通常はこのような依頼のほうが向いています：

- 「まずこのノードの detail を整理し、戦闘システムへの関係エッジを 1 本追加して」
- 「`src/game` 配下の関連コードを読んで、この設計項目が現在どこに落ちているか教えて」
- 「まだコードは書かないで。このグラフでどのノードがまだ足りないかをまとめて」

つまり、**作業の境界が明確なほど、結果は通常より安定します。**

### 2. 大きめの作業はステップに分ける

作業が小さくないなら、自分で複数のステップに分けるほうが通常はよいです。

例えば、次のように言うのではなく：

- 「このゲームプレイ機能を設計からコード、リソースまで全部仕上げて」

より安定する進め方は：

1. まず現在のグラフで何が欠けているか分析する
2. 次に欠けているノードとエッジを追加する
3. 次に関係しそうなコードファイルを特定する
4. その後で初めて実装そのものを書き始める

利点は：

- 各ステップがずれていないかを確認しやすい
- 長い作業の中で agent が自分の目標を取り違えにくい

### 3. 何を先にやり、何をまだやらないかを明示する

これはしばしば非常に役立ちます。

例えば：

- 「まず分析だけ。ファイルはまだ変更しないで」
- 「まず Graph だけ変更。コードには触れないで」
- 「まず現在の実装を読んで、それから修正案をちょうだい」
- 「まず変更するファイルを列挙して。確認するまで編集を待って」

これにより対話がより制御しやすくなり、プロジェクト型の作業にずっと向いています。

## 何を妥当に期待できるか

現時点で、agent はおおよそ次のようなことに向いています：

### 1. 設計情報の理解と整理

例えば：

- 現在のグラフ内の設計ブロックが何を意味するか説明する
- ノードの detail を整理する手助けをする
- 欠けているノード、関係、構造を提案する
- 既存のグラフから現在の設計状態をまとめる

### 2. Graph の照会と変更

例えば：

- ノード、エッジ、それらの関係を見つける
- ノードとエッジを追加、削除、更新する
- グラフ構造の一部を調整する
- Inspector 関連のフィールドを通じて設計情報を埋める

### 3. プロジェクトファイルの読み取りと変更

例えば：

- ある実装がすでにどのファイルに含まれているか確認する
- 既存コードに局所的な変更を加える
- 設計に基づいてゲーム層の内容を追加する
- グラフの設計情報を少しずつプロジェクトファイルに落とす手助けをする

### 4. 一部のツール機能の利用

例えば：

- プロジェクト内のファイルや画像を読む
- ツールを通じて構造化処理を行う
- レイアウト、リソース、実行に関するいくつかの機能をトリガーする

そのため、その価値は質問に答えることだけではありません。**プロジェクトの文脈の中で実際の作業をすること**にも価値があります。

## 何を期待しすぎてはいけないか

agent は多くのことができますが、完全自動のプロジェクト完成機として理解すべきではありません。

次の領域で期待が高すぎると、失望しやすくなります。

### 1. 大きな作業を一発で完璧に仕上げると思い込まない

特に次が関わる場合：

- 大量の文脈
- 複数ファイルの変更
- グラフ、コード、リソースの同時調整
- あなたの美的・製品的判断が必要な作業

より現実的な期待は通常：

- 作業を前進させられる
- かなりの量の機械的・構造的作業を完了できる
- ただし、あなたの修正と方向付けがまだ必要

### 2. 言っていない意図を完全に理解すると思い込まない

頭の中に詳細なアイデアがあっても、実際に言わなければ、agent はそれを正しく推測できないかもしれません。

特に次のことは明示する価値があります：

- どのスタイルを優先したいか
- このステップが設計寄りか実装寄りか
- 保守的な変更がよいか、大胆な再構築がよいか
- いまは触れるべきでない領域はどこか

### 3. あらゆる能力の限界を無償で越えられると思い込まない

例えば：

- 現在のセッション文脈の理解は無限ではない
- provider 切り替えやモデル挙動の違いに対する耐性は限られる
- 一部の複雑な結果は、モデル自体の安定性にも左右される
- 一部の作業は一度に押し込むより、より小さく分けるほうがよい

## 非常に重要な境界：協働的な前進は得意だが、あなたの判断すべてを代替するのは得意でない

agent は次が比較的得意です：

- 物事を構造化する手助け
- 物事を実行する手助け
- 物事を検索する手助け
- 構造化された作業を前進させる手助け

しかし、次のようなより上位の判断をすべて代わりに行うのは本質的に得意ではありません：

- 最終的な製品上のトレードオフ
- 方向 A と B のどちらが正しいか
- どの表現があなたの長期的な美意識に最も合うか
- どの複雑な変更がいま行う価値があるか

これらは通常、最終的にあなたが決める必要がある判断です。

## 安定した使い方

Agent Console をよりスムーズで信頼できるものにしたいなら、安定したワークフローは通常：

1. まず現在の目標を述べる
2. 次にこの回の範囲を制限する
3. まず分析させる、またはまず計画を列挙させる
4. 方向がずれていないことを確認したら、変更を実行させる
5. ひとかたまりが終わったら、次のステップに進む

これは、非常に長い指示を 1 つ投げ込んで全部うまくいくのを期待するより、通常ずっと安定します。

## 結果が理想的でないときどうするか

結果がおかしいと感じたら、通常の優先順位は：

- 作業範囲を縮める
- このステップで何をすべきかを正確に述べる
- 欠けている文脈を補う
- 期待と合わない点を指摘する
- 一から再開させるのではなく、現在の結果を引き続き修復させる

単に「これは間違っている」と言うより、通常より効果的な言い方は：

- 「この方向はずれた。もっと保守的な変更がほしい」
- 「まだコードは書かないで。触れるファイルを列挙するだけにして」
- 「Graph の部分だけ扱って。コードはいまはそのままにして」
- 「現在の構造は保って。欠けているノードとエッジだけ追加して」

## 実用的な結論

Agent Console に対する最も健全な期待は通常：

- プロジェクトの文脈を理解する協働者になれる
- 多くの構造化された作業を完了する手助けができる
- 設計、Graph、ファイル、ツールの間を橋渡しできる
- ただし、方向付け、判断、最終レビューはあなたが行う必要がある

**作業ができる協働アシスタント**として扱えば、完全自動のブラックボックスとして扱うより、通常ずっと役立ちます。
