# コンパイルと実行（Execute）

Execute メニューは主に、現在のプロジェクトのコンパイル、実行、テストを担当します。

## これらのプロジェクト成果物はどう作られるか

現在のプロジェクトが生み出すゲームは、毎回まったく新しい工程としてゼロから作られるわけではありません。

より正確には、**固定の C++ プロジェクトテンプレート**の上で動作します：

- 下層にはすでに用意された工程構造がある
- これにはエンジン層、プラットフォーム層、リソースディレクトリ、ビルド設定、基本的なエントリポイントが含まれる
- 実際のプロジェクト開発では、主に **coding agent** が既存の設計に基づいて、このテンプレートに内容を少しずつ追加・修正していく

次のように理解できます：

- テンプレートが安定した骨格を提供する
- 設計が何を作るかを決める
- coding agent がその設計を骨格に少しずつ落とし込む

そのため、日常的な使用では `Compile / Run / Test` は単に「手書きコードの山をコンパイルする」だけではなく、むしろ次を検証するようなものです：

- 現在の設計がコード化に成功したか
- agent が書いた内容がテンプレート構造と互換性があるか
- ローカルのビルド環境が健全か

## Execute メニューに含まれるもの

- **Compile Project**：プロジェクトをコンパイル
- **Run Project**：プロジェクトを実行
- **Run Project (Debug)**：デバッグモードで実行
- **Run Test**：特定のテストを実行

推奨される順序は通常：

1. まず **Compile**
2. 次に **Run**
3. 特定の検証対象があれば、その後に **Test**

こうすることで、「ビルド失敗」と「実行時失敗」を切り分けやすくなります。

## Compile は何を検証しているか

コンパイルが成功すると、通常少なくとも次を意味します：

- 現在のプロジェクトコード構造が基本的に揃っている
- テンプレート工程自体が壊れていない
- ローカルのコンパイルパイプラインが利用可能
- agent の最近のコード変更がすぐにビルドを壊さなかった

そのため、新しいプロジェクトを初めて開いたとき、または大きめの agent 編集を行った直後は、`Compile` が最も重要な最初のステップになることが多いです。

## よくあるコンパイル失敗と、その調べ方の入り口

コンパイル失敗は、必ずしもプロジェクト全体が壊れていることを意味しません。多くの場合、ある層だけに問題があります。以下はよくあるいくつかのカテゴリです。

### 1. Provider / Agent が出力したコード自体に問題がある

例えば：

- 生成されたコードの構文が不完全
- 関数名、型名、ヘッダー参照が一致しない
- 異なる変更同士が整合していない

この種の問題は通常、次のように見えます：

- コンパイラが C++ の構文エラーを直接報告する
- ある symbol / type / include が見つからない
- 直近の agent 変更の後に突然エラーが始まる

試せること：

- 直近の一巡で agent が変更した内容を見直す
- 後続の連鎖エラーに気を取られず、最初のコンパイルエラーから見始める
- 最も前の、最も根本的な問題を先に直す

### 2. プロジェクト構造やファイルの配置が間違っている

例えば：

- ファイルが不適切な場所に書き込まれた
- 新しく追加したコードがテンプレートの既存構造と整合していない
- リソースパス、ヘッダーパス、ソースの構成がプロジェクトレイアウトと一致しない

この種の問題は通常、次のように見えます：

- include パスが壊れている
- ソースファイルやリソースファイルが見つからない
- 何かが明らかに書かれているのに、ビルドパイプラインが正しく拾えていない

試せること：

- 関連ファイルが想定したディレクトリにあるか確認する
- パス参照がプロジェクト構造と一致しているか確認する
- 変更が誤った領域にずれず、正しいプロジェクト層に落ちているか確認する

### 3. ローカルのビルド環境に問題がある

例えば：

- CMake やコンパイラ環境が不完全
- ビルドツールが利用できない
- ローカルの依存関係やツールチェーンの状態が壊れている

この種の問題は通常、次のように見えます：

- 実際のコンパイルが始まる前の configure 段階で失敗する
- 実際のビルドが始まる前にツールチェーンエラーが出る
- ある 1 つのプロジェクトだけが特別なのではなく、複数のプロジェクトがコンパイルに失敗する

試せること：

- まずこれが「プロジェクトコードの問題」か「環境の問題」かを切り分ける
- 最小のプロジェクトすらコンパイルできないなら、まず環境を疑う
- Quick Start の最小検証フローをもう一度たどる

## 実行とデバッグ

### Run Project

`Run Project` は現在のプロジェクトを直接起動するために使います。

次のような場面で役立ちます：

- コンパイルが成功したばかりで、すぐに現在の結果を見たい
- プログラムが正常に起動できることを手早く確認したい
- 最新の設計やコード変更が明らかな挙動変化を引き起こしたか確認したい

### Run Project (Debug)

`Run Project (Debug)` は実行時の問題を調べるときに向いています。例えば：

- コンパイルはできるが、起動時の挙動がおかしい
- ログ、状態、実行フローをより詳しく調べたい
- 「コンパイル時は問題ない」と「実行時のロジックが間違っている」を区別したい

### Run Test

`Run Test` は、検証したいテスト対象がすでに分かっているときに役立ちます。

プロジェクト全体を直接実行するのと比べて、より焦点が絞られており、次に向いています：

- 単一のテスト名を検証する
- 特定の問題を再現する
- ある 1 つのモジュールやシナリオを狭く確認する

## 実用的な提案

一巡の変更を終えたばかりなら、最も安全な順序は通常：

1. まず **Compile**
2. コンパイルが成功したら、次に **Run**
3. 実行時の挙動がおかしければ、**Debug / Test** を検討

`Compile` がまだ通らないなら、先に実行時の挙動を見ようと急がないでください。最初のビルドエラーを先に解決するほうが、通常はずっと効率的です。
