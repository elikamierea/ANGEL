# Agent Console 와 도구 호출

Agent Console 은 내장 agent 와 직접 협업하는 곳입니다.

실용적인 관점에서 보면, 사용하기 전에 agent 시스템 내부의 전체 오케스트레이션을 이해할 필요는 없습니다. 더 중요한 것은：

- 어떻게 말을 걸지
- 무엇을 시킬지
- 지금 그 작업을 해낼 수 있는지 어떻게 판단할지
- 그 능력의 경계를 어떻게 이해할지

## 먼저 무엇으로 여길 것인가

가장 실용적인 이해 방식은 보통 이렇습니다：

- 단순한 채팅 상자가 아님
- 한마디면 항상 작업 전체를 완벽하게 끝내는 마법 버튼도 아님
- **프로젝트 맥락을 읽고, 현재 설계를 이해하며, 도구를 사용해 작업을 수행하려는 협업 보조자**로 이해하는 것이 좋음

따라서 가장 잘 맞는 것은 매우 모호한 큰 소망이 아니라 다음과 같습니다：

- 명확한 목표
- 명확한 범위
- 우선 처리하길 원하는 명확한 첫 단계

## 사용자는 agent 와 어떻게 상호작용해야 하는가

### 1. 작업을 가능한 한 구체적으로

다음과 같이 말하는 것보다：

- 「이 프로젝트를 좋게 만들어」

보통 다음과 같은 요청이 더 적합합니다：

- 「먼저 이 노드의 detail 을 정리하고, 전투 시스템과의 관계 엣지를 하나 추가해」
- 「`src/game` 아래 관련 코드를 읽고, 이 설계 항목이 현재 어디에 떨어져 있는지 알려줘」
- 「아직 코드는 쓰지 말고, 이 그래프에서 어떤 노드가 아직 빠졌는지만 정리해」

다시 말해, **작업 경계가 명확할수록 결과는 보통 더 안정적입니다.**

### 2. 큰 작업은 단계로 나누기

작업이 작지 않다면, 직접 여러 단계로 나누는 것이 보통 더 좋습니다.

예를 들어 다음과 같이 말하지 말고：

- 「이 게임플레이 기능을 설계부터 코드, 리소스까지 다 끝내」

더 안정적인 방식은：

1. 먼저 현재 그래프에서 무엇이 빠졌는지 분석
2. 그다음 빠진 노드와 엣지를 추가
3. 그다음 어떤 코드 파일이 관여할지 찾기
4. 그 후에야 구현 자체를 쓰기 시작

이점은：

- 각 단계가 빗나가는지 확인하기 더 쉬움
- 긴 작업에서 agent 가 자신의 목표를 혼동하기 더 어려움

### 3. 먼저 무엇을 하고, 무엇을 아직 하지 말지 명시하기

이는 종종 매우 도움이 됩니다.

예를 들어：

- 「먼저 분석만. 파일은 아직 수정하지 마」
- 「먼저 Graph 만 수정. 코드는 건드리지 마」
- 「먼저 현재 구현을 읽고, 그다음 수정 방안을 줘」
- 「먼저 바꿀 파일을 나열해. 확인할 때까지 편집을 기다려」

이렇게 하면 상호작용이 더 제어 가능해지고, 프로젝트형 작업에 훨씬 적합합니다.

## 무엇을 합리적으로 기대할 수 있는가

현재 agent 는 대략 다음과 같은 일에 가장 적합합니다：

### 1. 설계 정보 이해와 정리

예：

- 현재 그래프의 어떤 설계 블록이 무엇을 의미하는지 설명
- 노드 detail 정리를 도움
- 빠진 노드, 관계, 구조를 제안
- 기존 그래프에서 현재 설계 상태를 요약

### 2. Graph 조회와 수정

예：

- 노드, 엣지와 그 관계를 찾기
- 노드와 엣지를 추가, 삭제, 갱신
- 그래프 구조의 일부를 조정
- Inspector 관련 필드를 통해 설계 정보 채우기

### 3. 프로젝트 파일 읽기와 수정

예：

- 어떤 구현이 이미 어떤 파일에 있는지 확인
- 기존 코드에 국소적 수정
- 설계에 따라 게임 계층 내용을 추가
- 그래프의 설계 정보를 점차 프로젝트 파일로 옮기는 것을 도움

### 4. 일부 도구 기능 사용

예：

- 프로젝트 내 파일이나 이미지를 읽기
- 도구를 통해 구조화 처리 수행
- 레이아웃, 리소스, 실행과 관련된 일부 기능 트리거

따라서 그 가치는 질문에 답하는 것만이 아닙니다. **프로젝트 맥락 안에서 실제 작업을 하는 것**에도 가치가 있습니다.

## 무엇을 너무 기대하면 안 되는가

agent 는 많은 일을 할 수 있지만, 완전 자동 프로젝트 완성기로 이해해서는 안 됩니다.

다음 영역에서 기대가 너무 높으면, 실망할 가능성이 훨씬 커집니다.

### 1. 큰 작업을 한 번에 완벽히 끝낼 거라고 가정하지 말기

특히 다음이 관련될 때：

- 많은 양의 맥락
- 여러 파일 변경
- 그래프, 코드, 리소스의 동시 조율
- 당신의 미적·제품적 판단이 필요한 작업

더 현실적인 기대는 보통：

- 작업을 전진시킬 수 있음
- 상당량의 기계적·구조적 작업을 완료할 수 있음
- 그러나 여전히 당신의 교정과 방향 제시가 필요함

### 2. 말하지 않은 의도를 완전히 이해할 거라고 가정하지 말기

머릿속에 이미 세밀한 생각이 있어도, 실제로 말하지 않으면 agent 가 정확히 추측하지 못할 수 있습니다.

특히 다음은 명시할 가치가 있습니다：

- 어떤 스타일을 우선하고 싶은지
- 이 단계가 설계 지향인지 구현 지향인지
- 보수적 수정을 원하는지 대담한 재구성을 원하는지
- 당분간 건드리면 안 되는 영역은 어디인지

### 3. 모든 능력 경계를 비용 없이 넘을 거라고 가정하지 말기

예：

- 현재 세션 맥락에 대한 이해는 무한하지 않음
- provider 전환이나 모델 동작 차이에 대한 내성은 제한적임
- 일부 복잡한 결과는 모델 자체의 안정성에도 영향받음
- 일부 작업은 한 번에 밀어넣기보다 더 작게 나누는 것이 나음

## 매우 중요한 경계：협업적 전진에는 강하지만, 당신의 판단 전부를 대체하는 데는 강하지 않음

agent 는 다음에 비교적 강합니다：

- 정리를 도움
- 실행을 도움
- 검색을 도움
- 구조화된 작업을 전진시킴

그러나 다음과 같은 상위 결정 전부를 대신 내리는 데는 본질적으로 강하지 않습니다：

- 최종 제품상의 절충
- 방향 A 와 B 중 어느 것이 옳은지
- 어떤 표현이 당신의 장기적 미감에 가장 맞는지
- 어떤 복잡한 변경이 지금 할 가치가 있는지

이런 부분은 보통 여전히 당신이 최종 결정을 내려야 합니다.

## 안정적인 사용 방식

Agent Console 을 더 매끄럽고 믿을 수 있게 쓰고 싶다면, 안정적인 워크플로는 보통：

1. 먼저 현재 목표를 말하기
2. 그다음 이번 회차의 범위를 제한하기
3. 먼저 분석하게 하거나, 먼저 계획을 나열하게 하기
4. 방향이 빗나가지 않음을 확인한 뒤, 수정을 실행하게 하기
5. 한 덩어리가 끝나면 다음 단계로 진행하기

이는 매우 긴 지시 하나를 그냥 던져 넣고 전부 잘 나오길 바라는 것보다 보통 훨씬 안정적입니다.

## 결과가 이상적이지 않을 때 어떻게 할까

결과가 잘못됐다고 느끼면, 보통의 우선순위는：

- 작업 범위를 줄이기
- 이 단계가 무엇을 해야 하는지 정확히 말하기
- 빠진 맥락을 보충하기
- 기대와 맞지 않는 점을 지적하기
- 처음부터 다시 시작하게 하지 말고, 현재 결과를 이어서 고치게 하기

단순히 「이건 틀렸어」라고 말하는 것보다, 보통 더 효과적인 표현은：

- 「이 방향은 빗나갔어. 더 보수적인 변경을 원해」
- 「아직 코드는 쓰지 마. 건드릴 파일만 나열해」
- 「Graph 부분만 처리해. 코드는 지금은 그대로 둬」
- 「현재 구조는 유지해. 빠진 노드와 엣지만 추가해」

## 실용적인 결론

Agent Console 에 대한 가장 건강한 기대는 보통：

- 프로젝트 맥락을 이해하는 협업자가 될 수 있음
- 많은 구조화된 작업을 완료하도록 도울 수 있음
- 설계, Graph, 파일, 도구 사이를 잇는 다리가 될 수 있음
- 그러나 여전히 당신이 방향을 제시하고, 판단하고, 최종 검수를 해야 함

**일을 할 수 있는 협업 보조자**로 여긴다면, 완전 자동 블랙박스로 여기는 것보다 보통 훨씬 유용합니다.
