# 컴파일과 실행（Execute）

Execute 메뉴는 주로 현재 프로젝트를 컴파일, 실행, 테스트하는 일을 담당합니다.

## 이 프로젝트 산출물은 어떻게 만들어지는가

현재 프로젝트가 만들어내는 게임은 매번 완전히 새로운 공정으로 처음부터 만들어지는 것이 아닙니다.

더 정확히 말하면, **고정된 C++ 프로젝트 템플릿** 위에서 작동합니다：

- 하부에 이미 준비된 공정 구조가 있음
- 여기에는 엔진 계층, 플랫폼 계층, 리소스 디렉터리, 빌드 설정, 기본 진입점이 포함됨
- 실제 프로젝트 개발에서는 주로 **coding agent** 가 기존 설계를 바탕으로 이 템플릿에 내용을 점차 추가하고 수정함

다음과 같이 이해할 수 있습니다：

- 템플릿이 안정적인 골격을 제공
- 설계가 무엇을 만들지 결정
- coding agent 가 그 설계를 골격에 점차 옮겨 넣음

따라서 일상적인 사용에서 `Compile / Run / Test` 는 단지 「손으로 쓴 코드 더미를 컴파일하는」 것만이 아니라, 오히려 다음을 검증하는 것에 가깝습니다：

- 현재 설계가 코드로 성공적으로 전환되었는지
- agent 가 쓴 내용이 템플릿 구조와 호환되는지
- 로컬 빌드 환경이 정상인지

## Execute 메뉴에 포함되는 것

- **Compile Project**：프로젝트 컴파일
- **Run Project**：프로젝트 실행
- **Run Project (Debug)**：디버그 모드로 실행
- **Run Test**：특정 테스트 실행

권장 순서는 보통：

1. 먼저 **Compile**
2. 그다음 **Run**
3. 특정 검증 대상이 있으면 그 후에 **Test**

이렇게 하면 「빌드 실패」와 「실행 시 실패」를 분리해서 보기 더 쉬워집니다.

## Compile 은 무엇을 검증하는가

컴파일이 성공하면 보통 최소한 다음을 의미합니다：

- 현재 프로젝트 코드 구조가 기본적으로 완전함
- 템플릿 공정 자체가 망가지지 않음
- 로컬 컴파일 파이프라인이 사용 가능
- agent 의 최근 코드 변경이 즉시 빌드를 깨뜨리지 않음

따라서 새 프로젝트를 처음 열었을 때, 또는 비교적 큰 agent 편집을 한 직후에는 `Compile` 이 가장 중요한 첫 단계가 되는 경우가 많습니다.

## 흔한 컴파일 실패와, 먼저 어떻게 점검할까

컴파일 실패가 반드시 프로젝트 전체가 망가졌음을 뜻하지는 않습니다. 많은 경우 어느 한 계층에만 문제가 있습니다. 아래는 비교적 흔한 몇 가지 범주입니다.

### 1. Provider / Agent 가 출력한 코드 자체에 문제가 있음

예：

- 생성된 코드의 구문이 불완전함
- 함수명, 타입명, 헤더 참조가 일치하지 않음
- 변경 사항끼리 서로 맞지 않음

이런 문제는 보통 다음과 같이 나타납니다：

- 컴파일러가 C++ 구문 오류를 직접 보고함
- 어떤 symbol / type / include 를 찾지 못함
- 최근 agent 변경 후 갑자기 오류가 시작됨

시도할 것：

- 최근 한 차례 agent 가 무엇을 바꿨는지 되짚어 보기
- 이후의 연쇄 오류에 휘둘리지 말고 첫 번째 컴파일 오류부터 보기
- 가장 앞의, 가장 근본적인 오류를 먼저 고치기

### 2. 프로젝트 구조나 파일 위치가 잘못됨

예：

- 파일이 부적절한 위치에 쓰임
- 새로 추가한 코드가 템플릿의 기존 구조와 맞지 않음
- 리소스 경로, 헤더 경로, 소스 구성이 프로젝트 레이아웃과 일치하지 않음

이런 문제는 보통 다음과 같이 나타납니다：

- include 경로가 깨짐
- 소스 파일이나 리소스 파일을 찾지 못함
- 분명히 「썼는데」 빌드 파이프라인이 제대로 받아들이지 못함

시도할 것：

- 관련 파일이 예상한 디렉터리에 있는지 확인
- 경로 참조가 프로젝트 구조와 일치하는지 확인
- 변경이 엉뚱한 영역으로 빗나가지 않고 올바른 프로젝트 계층에 들어갔는지 확인

### 3. 로컬 빌드 환경 문제

예：

- CMake 나 컴파일러 환경이 불완전함
- 빌드 도구를 사용할 수 없음
- 로컬 의존성이나 툴체인 상태가 깨짐

이런 문제는 보통 다음과 같이 나타납니다：

- 실제 컴파일이 시작되기 전 configure 단계에서 실패함
- 실제 빌드가 시작되기 전에 툴체인 오류가 나타남
- 한 프로젝트만 특별한 게 아니라 여러 프로젝트가 컴파일에 실패함

시도할 것：

- 먼저 이것이 「프로젝트 코드 문제」인지 「환경 문제」인지 구분
- 최소 프로젝트조차 컴파일되지 않으면 먼저 환경을 의심
- Quick Start 의 최소 검증 흐름을 다시 한번 따라가기

## 실행과 디버그

### Run Project

`Run Project` 는 현재 프로젝트를 직접 실행하는 데 사용됩니다.

다음과 같은 상황에서 유용합니다：

- 컴파일이 막 성공해서 현재 결과를 바로 보고 싶음
- 프로그램이 정상적으로 시작되는지 빠르게 확인하고 싶음
- 최근 한 차례의 설계나 코드 변경이 뚜렷한 동작 변화를 일으켰는지 확인하고 싶음

### Run Project (Debug)

`Run Project (Debug)` 는 실행 시 문제를 조사할 때 더 적합합니다. 예：

- 컴파일은 되지만 시작 후 동작이 잘못됨
- 로그, 상태, 실행 흐름을 더 자세히 살펴보고 싶음
- 「컴파일 시점은 문제없음」과 「실행 시 로직이 잘못됨」을 구분하고 싶음

### Run Test

`Run Test` 는 검증하려는 테스트 대상을 이미 알고 있을 때 유용합니다.

전체 프로젝트를 직접 실행하는 것보다 더 집중적이며, 다음에 적합합니다：

- 단일 테스트 이름을 검증
- 특정 문제를 재현
- 한 모듈이나 시나리오를 좁게 확인

## 실용적인 제안

한 차례 변경을 막 마쳤다면, 가장 안전한 순서는 보통：

1. 먼저 **Compile**
2. 컴파일이 성공하면 그다음 **Run**
3. 실행 동작이 잘못되면 **Debug / Test** 고려

`Compile` 조차 통과하지 못하면, 먼저 실행 결과를 보려고 서두르지 마세요. 가장 앞의 빌드 오류를 먼저 해결하는 편이 보통 훨씬 효율적입니다.
