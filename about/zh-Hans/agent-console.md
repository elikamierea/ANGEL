# Agent Console 与工具调用

Agent Console 是你和内置 agent 直接协作的地方。

从使用角度看，你不需要先理解整套 agent 系统内部是怎么编排的。更重要的是：

- 该怎么跟它说话
- 该让它做什么
- 该如何判断它现在能不能胜任这件事
- 该如何理解它的能力边界

## 先把它当成什么

最实用的理解方式通常是：

- 它不是单纯的聊天框
- 也不是“你说一句，它必定一次做完”的魔法按钮
- 它更像是一个**可以读取项目上下文、理解当前设计、并尝试调用工具去执行任务的协作助手**

所以最适合它的，不是非常模糊的大愿望，而是：

- 明确目标
- 明确范围
- 明确你想让它优先做哪一步

## 用户应该怎样和 agent 交互

### 1. 尽量把任务说具体

比起：

- “把这个项目弄好”

更适合的说法通常是：

- “先帮我整理这个节点的 detail，并补一条和战斗系统的关系边”
- “请读取 `src/game` 里相关代码，看看这个设计项目前落在哪里”
- “先不要写代码，只帮我总结这个图里还缺哪些节点”

也就是说，**越明确的任务边界，越容易得到稳定结果。**

### 2. 复杂任务尽量分步骤

如果任务本身不小，建议主动拆成几步。

例如不要一口气说：

- “把这个玩法从设计到代码到资源都做完”

而更建议：

1. 先分析当前图里缺什么
2. 再补节点和边
3. 再定位会落到哪些代码文件
4. 最后再开始写具体实现

这样做的好处是：

- 你更容易检查每一步有没有跑偏
- agent 也更不容易在长任务里混淆目标

### 3. 明确告诉它“先做什么，不做什么”

这通常会非常有帮助。

例如：

- “先只分析，不要改文件”
- “先只改 Graph，不要动代码”
- “先读现有实现，再给我一个修改方案”
- “先列出会改哪些文件，确认后再写”

这会让交互更可控，也更适合项目型工作。

## 你可以期待它做什么

当前更适合期待 agent 做的事情，大致包括：

### 1. 理解和整理设计信息

例如：

- 解释当前图里某个设计块的含义
- 帮你整理节点 detail
- 建议缺失的节点、关系或结构
- 根据现有图总结当前设计状态

### 2. 查询与修改 Graph

例如：

- 查找节点、边和它们的关系
- 增删改节点与边
- 调整图中的部分结构
- 结合 Inspector 字段补充设计信息

### 3. 读取和修改项目文件

例如：

- 查看某些实现已经落在哪些文件
- 对现有代码做局部修改
- 依据设计去补充游戏层内容
- 协助把图中的设计信息逐步落到项目文件中

### 4. 调用部分工具能力

例如：

- 读取项目内文件或图像
- 结合工具做结构化处理
- 触发与布局、资源、执行相关的一些能力

所以它的价值不只是“回答问题”，而是**在项目上下文里做一些实际工作**。

## 你不应该过度期待什么

虽然 agent 能做的事情不少，但也不要把它理解成“全自动项目完成器”。

下面这些预期，如果放得太高，通常更容易失望：

### 1. 不要默认它一次就能把大任务完美做完

尤其是涉及：

- 大量上下文
- 多文件改动
- 图、代码、资源同时联动
- 需要你做审美判断或产品判断的任务

更现实的预期通常是：

- 它能帮你推进
- 能完成相当一部分机械和结构化工作
- 但仍需要你持续校对和给方向

### 2. 不要默认它永远完全理解你的隐含意图

如果你脑中已经有很细的想法，但没有说出来，agent 不一定会刚好猜中。

尤其是下面这些内容，最好明确说：

- 你优先想要哪种风格
- 你这一步是偏设计还是偏实现
- 你要保守修改还是大胆重构
- 哪些区域暂时不要碰

### 3. 不要默认它能无代价跨越所有能力边界

例如：

- 它对当前会话上下文的理解不是无限的
- 它对 provider 切换和不同模型行为差异的承受能力有限
- 某些复杂结果仍然会受模型本身稳定性影响
- 有些任务可能更适合拆小，而不是一次压给它

## 一个很重要的边界：它擅长“协作推进”，不擅长“替你做全部判断”

Agent 比较擅长的是：

- 帮你梳理
- 帮你执行
- 帮你查找
- 帮你把结构化任务往前推

但它不天然擅长替你做所有高层判断，例如：

- 最终产品取舍
- 设计方向到底选 A 还是 B
- 哪种表达最符合你的长期审美
- 哪种复杂改动最值得现在就做

这些地方，通常仍然需要你来拍板。

## 一个比较稳的使用方式

如果你想把 Agent Console 用得更顺，比较稳的工作方式通常是：

1. 先说明当前目标
2. 再限制本轮范围
3. 让它先分析或先列计划
4. 确认方向没跑偏后，再让它执行修改
5. 每完成一段，再进入下一步

这会比“一个超长指令直接全扔进去”稳定得多。

## 如果结果不理想，该怎么调

如果你觉得结果不对，通常优先这样处理：

- 缩小任务范围
- 明确这一步只做什么
- 补充上下文
- 指出哪里不符合预期
- 让它基于刚才结果继续修，而不是完全重来

比起简单说“这不对”，更有效的说法通常是：

- “这个方向偏了，我要的是更保守的改动”
- “先不要写代码，只列出准备改哪些文件”
- “你只处理 Graph 那部分，代码部分先别碰”
- “保留现有结构，只补缺失节点和边”

## 一个实用结论

最适合 Agent Console 的期待通常是：

- 它能成为一个懂项目上下文的协作者
- 能帮你完成很多结构化工作
- 能在设计、Graph、文件和工具之间搭桥
- 但它仍然需要你给方向、做判断、做验收

如果你把它当成“会做事的协作助手”，通常会比把它当成“全自动黑盒”更好用。
