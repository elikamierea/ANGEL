# Agent Console 與工具呼叫

Agent Console 是你和內建 agent 直接協作的地方。

從使用角度看，你不需要先理解整套 agent 系統內部是怎麼編排的。更重要的是：

- 該怎麼跟它說話
- 該讓它做什麼
- 該如何判斷它現在能不能勝任這件事
- 該如何理解它的能力邊界

## 先把它當成什麼

最實用的理解方式通常是：

- 它不是單純的聊天框
- 也不是「你說一句，它必定一次做完」的魔法按鈕
- 它更像是一個**可以讀取專案上下文、理解目前設計、並嘗試呼叫工具去執行任務的協作助手**

所以最適合它的，不是非常模糊的大願望，而是：

- 明確目標
- 明確範圍
- 明確你想讓它優先做哪一步

## 使用者應該怎樣和 agent 互動

### 1. 盡量把任務說具體

比起：

- 「把這個專案弄好」

更適合的說法通常是：

- 「先幫我整理這個節點的 detail，並補一條和戰鬥系統的關係邊」
- 「請讀取 `src/game` 裡相關程式碼，看看這個設計項目前落在哪裡」
- 「先不要寫程式碼，只幫我總結這個圖裡還缺哪些節點」

也就是說，**越明確的任務邊界，越容易得到穩定結果。**

### 2. 複雜任務盡量分步驟

如果任務本身不小，建議主動拆成幾步。

例如不要一口氣說：

- 「把這個玩法從設計到程式碼到資源都做完」

而更建議：

1. 先分析目前圖裡缺什麼
2. 再補節點和邊
3. 再定位會落到哪些程式碼檔案
4. 最後再開始寫具體實作

這樣做的好處是：

- 你更容易檢查每一步有沒有跑偏
- agent 也更不容易在長任務裡混淆目標

### 3. 明確告訴它「先做什麼，不做什麼」

這通常會非常有幫助。

例如：

- 「先只分析，不要改檔案」
- 「先只改 Graph，不要動程式碼」
- 「先讀現有實作，再給我一個修改方案」
- 「先列出會改哪些檔案，確認後再寫」

這會讓互動更可控，也更適合專案型工作。

## 你可以期待它做什麼

目前更適合期待 agent 做的事情，大致包括：

### 1. 理解和整理設計資訊

例如：

- 解釋目前圖裡某個設計塊的含義
- 幫你整理節點 detail
- 建議缺失的節點、關係或結構
- 根據現有圖總結目前設計狀態

### 2. 查詢與修改 Graph

例如：

- 查找節點、邊和它們的關係
- 增刪改節點與邊
- 調整圖中的部分結構
- 結合 Inspector 欄位補充設計資訊

### 3. 讀取和修改專案檔案

例如：

- 檢視某些實作已經落在哪些檔案
- 對現有程式碼做局部修改
- 依據設計去補充遊戲層內容
- 協助把圖中的設計資訊逐步落到專案檔案中

### 4. 呼叫部分工具能力

例如：

- 讀取專案內檔案或影像
- 結合工具做結構化處理
- 觸發與配置、資源、執行相關的一些能力

所以它的價值不只是「回答問題」，而是**在專案上下文裡做一些實際工作**。

## 你不應該過度期待什麼

雖然 agent 能做的事情不少，但也不要把它理解成「全自動專案完成器」。

下面這些預期，如果放得太高，通常更容易失望：

### 1. 不要預設它一次就能把大任務完美做完

尤其是涉及：

- 大量上下文
- 多檔案改動
- 圖、程式碼、資源同時連動
- 需要你做審美判斷或產品判斷的任務

更現實的預期通常是：

- 它能幫你推進
- 能完成相當一部分機械和結構化工作
- 但仍需要你持續校對和給方向

### 2. 不要預設它永遠完全理解你的隱含意圖

如果你腦中已經有很細的想法，但沒有說出來，agent 不一定會剛好猜中。

尤其是下面這些內容，最好明確說：

- 你優先想要哪種風格
- 你這一步是偏設計還是偏實作
- 你要保守修改還是大膽重構
- 哪些區域暫時不要碰

### 3. 不要預設它能無代價跨越所有能力邊界

例如：

- 它對目前工作階段上下文的理解不是無限的
- 它對 provider 切換和不同模型行為差異的承受能力有限
- 某些複雜結果仍然會受模型本身穩定性影響
- 有些任務可能更適合拆小，而不是一次壓給它

## 一個很重要的邊界：它擅長「協作推進」，不擅長「替你做全部判斷」

Agent 比較擅長的是：

- 幫你梳理
- 幫你執行
- 幫你查找
- 幫你把結構化任務往前推

但它不天然擅長替你做所有高層判斷，例如：

- 最終產品取捨
- 設計方向到底選 A 還是 B
- 哪種表達最符合你的長期審美
- 哪種複雜改動最值得現在就做

這些地方，通常仍然需要你來拍板。

## 一個比較穩的使用方式

如果你想把 Agent Console 用得更順，比較穩的工作方式通常是：

1. 先說明目前目標
2. 再限制本輪範圍
3. 讓它先分析或先列計畫
4. 確認方向沒跑偏後，再讓它執行修改
5. 每完成一段，再進入下一步

這會比「一個超長指令直接全扔進去」穩定得多。

## 如果結果不理想，該怎麼調

如果你覺得結果不對，通常優先這樣處理：

- 縮小任務範圍
- 明確這一步只做什麼
- 補充上下文
- 指出哪裡不符合預期
- 讓它基於剛才結果繼續修，而不是完全重來

比起單純說「這不對」，更有效的說法通常是：

- 「這個方向偏了，我要的是更保守的改動」
- 「先不要寫程式碼，只列出準備改哪些檔案」
- 「你只處理 Graph 那部分，程式碼部分先別碰」
- 「保留現有結構，只補缺失節點和邊」

## 一個實用結論

最適合 Agent Console 的期待通常是：

- 它能成為一個懂專案上下文的協作者
- 能幫你完成很多結構化工作
- 能在設計、Graph、檔案和工具之間搭橋
- 但它仍然需要你給方向、做判斷、做驗收

如果你把它當成「會做事的協作助手」，通常會比把它當成「全自動黑盒」更好用。
