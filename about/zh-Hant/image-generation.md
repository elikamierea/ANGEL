# 圖像生成

> 本頁講的是如何讓 agent 為你的專案生成圖像，以及——同樣重要的——你應該對它抱有怎樣的現實預期。

## 圖像生成在工作流中的位置

圖像生成通常**不是**你最先做的事。更實際的順序是：

1. 先搭好設計（Graph），讓 agent **用佔位圖**（placeholder：純色塊、簡單的矩形/圓形等）來實作玩法與邏輯。
2. 讓這套基於佔位圖的版本能**編譯並執行**，確保機制大致正確。
3. **到這一步之後**，再開始用生成的圖像替換佔位圖。

原因很簡單：美術是最後才值得投入的部分。如果機制還在改，反覆重做美術就是浪費。

## 「生成 → 放進去 → 測試」的循環

當佔位版本大致能跑起來後，圖像生成就變成一個**反覆迭代的循環**，而不是一次性的步驟：

1. **生成**——為某個具體元素（玩家、金幣、敵人、背景……）生成一張圖。
2. **放進去**——把它存進專案，並在程式碼裡替換掉原本的佔位圖。
3. **執行並除錯**——真正把專案跑起來，在**真實場景**裡、**真實尺寸**下、**真實背景**前看效果。
4. **重新生成**——根據看到的效果，調整描述再生成一次。

每個素材通常都要繞這個循環好幾遍。單看一張孤立的圖說明不了什麼；**把它放進執行中的場景裡看**，才知道它行不行。

在 ANGEL 裡的接法：

- 建立專案時選帶圖像生成的範本——**Default（+圖像生成）** 或 **Extended（+圖像生成）**——這樣專案裡就會帶上 resource-provider 這個 agent。參見 (專案建立與開啟（New/Open/Save）)[project-io.md]。
- 生成的圖會儲存在 `assets/generated/images/` 下，其路徑會回傳給 agent，所以它能引用這些圖、並餵給 Create Sprite 等工具。參見 (Create Sprite)[create-sprite.md]。
- 圖像生成目前是 OpenAI（API key）的能力。你可以在 **設定 → Agent Model** 裡選一個具體的圖像模型，或保持 auto。

## 一個非常重要的預期：效果無法保證

這一點值得直說：

**目前各家的圖像模型——無一例外——都還不足以讓生成的圖片完美貼合一個風格化的、具體的場景。最終效果無法保證。**

具體來說意味著：

- 一張生成的圖單看可能沒問題，但一放進你的場景就不對勁——風格不對、比例不對、剪影不對、在背景前的顏色不對。
- 在大量素材之間保持**統一的美術風格**尤其困難。
- 嚴格的約束（精確的姿態、精確的視角、像素級精確的邊緣、乾淨的透明去背、「同一個角色但轉向左邊」）往往無法穩定達成。
- 多迭代會有幫助，但存在上限：有些效果用目前的模型就是做不到。

所以健康的用法是：

- 把生成的美術當作**從佔位圖快速到達「夠用」的手段**，而不是用來取得最終可交付、風格完美統一的成品美術。
- 描述裡把關鍵點說具體（主體、剪影、配色、背景該透明還是純色），但也要接受有些要求就是實作不了。
- 做好**最後一哩靠自己**的準備——手動修圖，或把最重要的素材換成手工製作的美術。
- 想清楚哪些素材真的需要風格統一，把迭代花在那裡；不重要的素材就讓它粗糙著。

## 一個實用的結論

- 先在佔位圖上把機制做對；跑起來之後再引入圖像生成。
- 預期是一個「生成 → 放進去 → 執行 → 重新生成」的循環，並且要在真實場景裡判斷效果。
- 不要指望完美、完全貼合風格的結果——目前模型無法保證這一點，所以要為迭代與手動收尾留出餘地。
